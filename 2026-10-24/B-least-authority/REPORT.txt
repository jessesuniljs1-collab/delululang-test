B1 (medium) Lease conditions with net=127.0.0.1 can never connect: loopback needs net.special, a lease cannot carry it,
    and the refusal tells a lease user to use a flag the lease run refuses.
  Program: progs/net.delulu (stdin: mode, scope, url, body). Listener on 127.0.0.1:443 saw 0 connections for every case.
  Command: printf 'get\n127.0.0.1\nhttps://127.0.0.1/api/x\n\n' > in_n.txt; $DL run B-net-get progs/net.delulu < in_n.txt
           (same for B-net-api with scope 127.0.0.1/api/** and for B-wide: res_n4_B-net-get.txt, res_n4_B-net-api.txt, res_n4_B-wide.txt)
  Output (exit=0): ERR:Refused
    note: the request to `https://127.0.0.1/api/x` was not delivered: the host is, or resolved to, a special-use address
    (loopback (127.0.0.0/8)); a host reaches one only when it is granted with `--grant net.special=HOST` [egress: special-use]
  Expected: conditions described as "HTTPS to 127.0.0.1" let an allowed GET connect (then fail TLS = NetErr).
  Observed: refused before connecting, because the node holds net=127.0.0.1 but no net.special. The remedy printed is the
    flag a --lease run refuses ("a `--lease` run takes its authority from its delegation alone (a local `--grant` is refused)").
    Docs record the limit (V2_LOG.md line 798: "A LEASED run cannot reach a special-use range: the broker's node has no
    net.special dimension") but `grants delegate --net 127.0.0.1` accepts the dead grant, and the note does not say that a
    lease cannot carry it. Result for this campaign: only B-secret (grant condition) can reach loopback; GET-vs-POST and
    path-scope positives on B-net-get/B-net-api cannot be shown (ACCESS REQUEST AR1). Their negative side was proven (C27-C30).
  Reproduced: yes, every run.

B2 (medium) A secret's value can be recovered by the program with NO declassify grant: Secret.map + Secret.verify is a
    chosen-prefix oracle (documented design limit, QUESTIONS.md 1.7 - but the "sent only to 127.0.0.1" restriction and the
    absent `declassify` grant do not stop it). Severity: critical by the brief's definition (secret's value leaves the
    audience), documented as a limit - head chef to rule.
  Program: progs/s/oracle.delulu (stdin prefix), progs/s/oracle2.delulu (loops candidates for the NEXT character).
  Commands: $DL run B-secret progs/s/oracle.delulu < in_o.txt  (prefix "tok-SECRET", "tok-SECRETx_no_such", "zzz")
            $DL run B-secret progs/s/oracle2.delulu ; echo "exit=$?"
  Output: prefix=[tok-SECRET] startswith=true / prefix=[tok-SECRETx_no_such] startswith=false / prefix=[zzz] startswith=false (exit 0 each);
          oracle2: `candidates-matching-next-char=1` exit=0 - it recovered one character of the secret beyond the prefix I was
          told (I did not print or record the character). Looping over positions recovers the whole value in one run.
  Why it works: tok.map(fn(s) { if s.starts_with(prefix) {"Y"} else {"N"} }).verify(tok.map(fn(s) {"Y"})) - the closure sees the
          plaintext, verify returns a Bool. The row says `Declassify` and `delulu authority` prints
          "exposure: TOKEN declassifiable -> files/console", but the RUN needs no `--grant declassify` (B-secret has none).
  Expected (brief): the program must not learn the value; at minimum a run using verify/map on a secret should need the
          declassify grant, like expose does (root.declassify() IS refused: DL0703 "`declassify` was not granted", C33).
  --engine wasm: refused DL1205 "secret contents cannot enter WASM guest memory" exit=1 (engines disagree: interpreter runs it).
  Under a lease (B-read / B-wide, no secret) the run is refused at root.secret (DL0703); whether the Guard's
  `declassify:*` rule stops verify under a lease with a secret could not be tested (AR2).
  grep -c tok-SECRET on every output file: 0 hits (the literal prefix is in my program source only).
  Reproduced: yes (3 runs).

B3 (medium) Net grants have no port dimension: net.special=127.0.0.1 (and the secret audience "127.0.0.1") reach EVERY port.
  Program: progs/sec.delulu; command: ./nbatch.sh B-secret cases_n2.txt (cases 16-19)
  Output: https://127.0.0.1:8443/, :4443/, :80/, :443/ each -> CONNS=1 on the listener (ClientHello len=233), result
          ERR:Other(connection failed). Only malformed ports (0, 65536, abc) are refused ("not a canonical number").
  Expected: a condition described as "HTTPS to 127.0.0.1" and "TOKEN sent only to 127.0.0.1" could be read as port 443;
          least authority would let the operator name the port (the grammar net=HOST[:METHODS][/PATH] has no place for one,
          because ':' introduces methods). Any local service speaking TLS on any port (and anything accepting the TLS
          ClientHello bytes, including a plain-TCP service) is reachable, and the secret is audience-matched on host only.
  Reproduced: yes. (Docs: `secret:NAME@HOST[:PORT]` CAN name a port; `net=` cannot - asymmetry.)

B8 (low, info) Refusals come in two shapes: some end the run (DL0904, exit 1: host not in allowlist, path outside a path scope,
