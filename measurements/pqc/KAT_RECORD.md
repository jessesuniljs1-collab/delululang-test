# NIST known-answer test vector search (Stage 10 phase 10i, Track G, invariant 51)

**What this record answers.** Invariant 51 (spec §8.2) says a PQC implementation "reach[es]
stable only after byte-exact validation against the official known-answer vectors, recorded in
the build order with vector provenance." Ruling D14b already found that KAT validation alone
would not be enough to reach stable even if the vectors were in hand, because the adopted crates
are independently unaudited by their own authors' statement — audit status is a second,
independent gate. That ruling is not revisited here. What *is* answered here, because D14b left
it open, is the narrower factual question: **can the official NIST vectors actually be obtained
from this machine, and if so, what do they look like?**

This record documents an actual attempt, not a description of one. Every source below was really
queried on 2026-07-20; outcomes are reported as observed, including the one that mattered.

## What was actually found (rows 3–7)

`usnistgov/ACVP-Server` — NIST's own GitHub organization, the source for the Automated
Cryptographic Validation Protocol server and tooling — ships a `gen-val/json-files/` folder that
the repository's own top-level README describes plainly:

> "This folder contains sample JSON files from all algorithms covered by the Gen/Vals. Use these
> when you would like to quickly grab a full set of files for testing. This includes registration,
> prompt, internalProjection, and expectedResults. These files are generated by the
> `NIST.CVP.ACVTS.Libraries.Generation.<Algo>.IntegrationTests` project under `GenValTests.cs`..."

In plain terms: these vectors are produced by NIST's own generation library — the same code that
backs the live ACVP Test System (ACVTS) that accredited labs use — and published so implementers
can self-test before, or without, engaging a lab. `prompt.json` is the question (what an
implementation-under-test is given), `expectedResults.json` is the answer key, and
`registration.json` declares which parameter sets and options were exercised. Every one of the
five directories below declares `ML-DSA-65` or `ML-KEM-768` among its tested parameter sets, and
pulling a matching `tgId`/`tcId` pair out of `prompt.json` and `expectedResults.json` produces a
real input→output pair — not a schema example. One was pulled and printed in full during this
search (ML-DSA-65 sigGen, `tgId=3`, `tcId=31`): a 4032-byte secret key and an 84-byte message went
in, a 3309-byte signature came out, byte-exact against NIST's own answer key.

## What this is not

- **Not a completed ACVP validation.** The live ACVTS is an authenticated service for accredited
  testing labs; reaching it requires a lab account and TOTP registration that this sandbox does not
  have and was not asked to obtain. What was fetched is NIST's own public self-test fixtures for
  the identical generation/validation code that service runs — the strongest provenance obtainable
  without lab credentials, but a distinct thing from a lab's signed validation certificate.
- **Not Wycheproof, not a third-party corpus, not self-generated.** Nothing here was substituted.
  Every byte in `measurements/pqc/vectors/` traces to a file inside `usnistgov/ACVP-Server`, and
  the provenance block in each saved file names the exact URL and git blob SHA1 so that claim is
  checkable by re-fetching.
- **Does not close ruling D14b.** D14b blocks stable on two independent facts: vectors not in
  hand, and the crates being unaudited by their own authors' admission. This record changes the
  first fact — the vectors *are* now in hand — but does nothing about the second. The audit gap is
  unaffected and post-quantum operations remain behind `--unstable` under DL1910. Whether D14's
  text should be updated to reflect that the first fact has changed is a build-order decision, not
  one this record makes.
- **Does not cover ML-KEM at all in the bonus test below.** `crates/delulu-runtime/src/pqc.rs`
  currently implements only the ML-DSA (signature) half of Track G; `ml-kem` is a pinned dependency
  (`Cargo.toml`) that is not yet called from anywhere in this crate. There is, today, no pqc.rs
  function to run an ML-KEM vector through.

range from ~560 KB combined (ML-KEM keyGen) to ~7.6 MB combined (ML-DSA sigGen, which covers 24
test groups across three parameter sets, message-length sweeps, and every hash/interface/preHash
combination).
Per this task's own instruction, a representative subset is saved instead of the multi-megabyte
originals. Each `sample_vectors_subset.json` states, in its own `_provenance` block, exactly how
many test cases it kept out of how many were available, plus the origin URL and git blob SHA1 of
the *complete, untouched* original file — so the full originals remain independently re-fetchable
and this subset's fidelity is checkable, rather than asking anyone to trust a paraphrase.

## The bonus check: one KAT run through `pqc.rs`

A minimal test was added to `crates/delulu-runtime/src/pqc.rs`'s existing test module:
`nist_acvp_ml_dsa_65_keygen_seed_to_pk_matches`. **It passed: 3/3.**

What it actually checks: for each of three official NIST vectors, feeding the vector's `seed`
through `ml_dsa_sign` — the real function `pqc.rs` uses for signing, not a re-derivation of it —
and slicing out the verifying-key bytes at the front of its output reproduces NIST's own `pk`
byte-for-byte.

What it does **not** check, stated as plainly as the things it does:

- **Not `sk`.** The `ml-dsa` crate (v0.1.1, the exact pinned version) exposes no public encoder
  for the raw FIPS-204 secret-key byte layout — `SigningKey`'s only public export is the 32-byte
  seed it was built from, not the 4032-byte encoded form NIST's vectors carry. There is nothing on
  this crate's public API to compare NIST's `sk` field against, so it wasn't compared. This is a
  crate API limitation, not a decision to skip a check that was possible.
- **Not sigGen.** ACVP's sigGen vectors hand you an already-expanded `sk` (the 4032-byte form),
  not a seed — and per the point above, this crate has no way to construct a signing key from that
  form. sigGen vectors were obtained (see table above) but could not be run through this crate.
- **Not sigVer**, despite being obtained and, at first look, promising: sigVer vectors carry
  `pk` + `message` + `context` + `signature` + expected pass/fail, and `pk ++ signature` is exactly
  the blob shape `ml_dsa_verify` parses. The blocker is `ML_DSA_CTX`: `pqc.rs` signs and verifies
  under one fixed domain-separator context (`b"delulu-artifact-v1"`), by design (it is what keeps a
  DeluluLang artifact signature from being replayable elsewhere), while ACVP's vectors carry their
  own per-vector `context` value. FIPS 204 folds the context into what gets signed, so a signature
  made under one context does not verify under a different one — feeding an ACVP vector through
  `ml_dsa_verify` as-is would fail on a context mismatch that has nothing to do with whether the
  cryptography is correct. Checking sigVer honestly would mean calling the raw crate's
  `verify_with_context` with the vector's own context, which is testing the crate again, not
  `pqc.rs` (`pqc.rs` has no entry point that takes an arbitrary context). Not attempted, for that
  reason, rather than attempted and hidden.
- **Not ML-KEM.** No function in `pqc.rs` calls `ml-kem` yet (see "What this is not," above), so
  there is nothing of `pqc.rs`'s to run an ML-KEM vector through.

So: one real, passing, byte-exact check against official NIST data, through the project's own
signing code — and four named reasons the rest of what was obtained couldn't be run the same way
today. Full suite re-run after the change: `cargo test -p delulu-runtime --lib` — **130/130
passed**, including the new test and every pre-existing one (no-default-features build; the
`python` feature is orthogonal to this file and was not touched).

## Reproducing

```
cargo test -p delulu-runtime --lib pqc::tests::nist_acvp_ml_dsa_65_keygen_seed_to_pk_matches
```

The vector re-derivation above can be repeated independently of this repo by fetching
`https://raw.githubusercontent.com/usnistgov/ACVP-Server/master/gen-val/json-files/ML-DSA-sigGen-FIPS204/prompt.json`
and `.../expectedResults.json`, matching `tgId=3`/`tcId=31`, and checking the `message`/`sk` pair
against the `signature` — exactly what was done by hand during this search before any file was
written.

## Bottom line

**Official NIST ACVP known-answer vectors for ML-DSA-65 and ML-KEM-768 were obtained** from
`usnistgov/ACVP-Server`, NIST's own repository — real input→output pairs, not descriptive
documentation, with checkable provenance (URL + git blob SHA1) saved alongside every subset. One
of those vectors was run through this project's actual signing code and matched byte-for-byte.

This closes the factual half of ruling D14b that said the vectors were not in hand — they now are,
for two of the two algorithms this project depends on, across five ACVP test types (keyGen,
sigGen, sigVer, and both halves of ML-KEM). **It does not close D14b's ruling.** The independent
audit gap D14b identified is untouched by anything in this record: the `ml-dsa` and `ml-kem`
crates remain, by their own authors' statement, never independently audited, and every
post-quantum operation in this codebase still refuses without `--unstable` under DL1910. Whether
having the vectors in hand changes anything about how D14 itself should be worded is a build-order
decision for the next phase, not a conclusion this record is positioned to draw.
