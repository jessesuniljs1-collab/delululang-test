VERDICT (two findings):
1. LEAK — chmod is a silent no-op on 9p: a 0700 dir and 0600 file read back as mode=777, and
   the SEPARATE account (uid 1003) read the "0600" probe.txt ("topsecret") AND the broker's
   32-byte broker.key (the lease-MAC secret). Every set_permissions delulu relies on is
   discarded (let _ = ...), so it cannot tell the hardening failed. Any secret delulu writes to
   a non-POSIX filesystem (9p/DrvFs, and by the same mechanism NFS/SMB/exFAT/FAT) is world-readable.
2. BIND-FAIL — the broker cannot bind its AF_UNIX socket on 9p: "Operation not supported
   (os error 95)". So it fails to serve there — but only AFTER writing a world-readable broker.key.
   (This is why the attacker's socket connect / grants list return ENOENT: no socket was ever bound.)

So the separate-account boundary that Scenario 1 proved on ext4 is ABSENT on a Windows-mounted
volume. This is a deployment hazard (category 7 — an OS/filesystem property), not a same-account
break: the default WSL /home is ext4. Mitigation shipped: verify the achieved perms after chmod
and warn when they did not stick (see the P21 hardening commit).
