# Sandbox threat model — boundaries, trusted computing base, assumptions, evidence

**Written:** 2026-09-17. **Status:** proposed; binds the design in `SANDBOX_ARCHITECTURE.md`.
**Discipline:** every claim is placed in one of `docs/MATHEMATICS.md`'s seven categories, and the
category is stated *before* any code exists so that the implementation phase knows what evidence it
owes. Nothing below is currently true of the binary; it is what would become true and how it would
be shown.

---

## 1. The adversary

Sandboxed code is assumed to be **any of**: buggy; malicious; AI-generated by a model that is
prompt-injected or misaligned; deliberately trying to escape; exfiltrating secrets; attacking the
network, the host, another guest, the runtime, dependencies or plugins. It may be a *well-typed
DeluluLang program* (then the language bounds it, and the sandbox exists for the day the checker
is wrong — 2026-08-03 was such a day), a *foreign library* (outside the proof by construction), or
a *plugin* (bounded by its grant if the loader is right). It runs, unless told otherwise, **as the
operator's own OS user** — the deployment this language markets to, and the one
`ROOT_ISSUANCE_TRUST_BOUNDARY.md` names as category 7.

The adversary is not assumed to be the operator, root, the kernel, the hypervisor, or the
hardware (Constitution §5.14). Side channels are out of scope at every level.

## 2. Boundaries per level, and what is trusted

| Level | Boundary enforced by | Trusted computing base (must be correct) | Not trusted (may be hostile) |
|---|---|---|---|
| L0 `none` | the checker + the runtime's own checks | compiler, runtime, primitive table, OS | the program's *intent* only |
| L1 `process` | the host kernel's process isolation, as configured by the launcher | host kernel; the launcher's use of namespaces/Landlock/seccomp/tokens/jobs/Seatbelt; the **channel parser**; the host effect proxy; the guest runtime binary's *integrity* (not its behaviour) | everything in the guest, including the interpreter once the program runs |
| L2 `microvm` | KVM + the VMM | host kernel's KVM; the VMM (Firecracker/CLH) and its jailer; the vsock device; the channel parser; the host effect proxy; the guest image's integrity | the whole guest: kernel, init, interpreter, program |
| L3 `external` | the operator's environment | the operator's environment **plus** everything in L1's list on the host side | the guest; the transport if not authenticated (must be) |
| L4 `attested` | hardware root of trust + L2/L3 | the attestation verifier and the hardware | the guest until it attests |

**The channel parser is in the TCB at every level ≥ 1.** It is the one component hostile bytes
reach from inside the boundary. It therefore gets the treatment the audit chain got: bounded
frames, canonical CBOR, a fixed request schema, no allocation proportional to untrusted length
before the bound check, fuzzed (category 6) and property-tested (category 4), and written once
for every backend.

## 3. Claims, and the evidence each owes

| # | Claim | Level | Category owed | How it would be shown |
|---|---|---|---|---|
| T1 | The guest holds no capability material, no secret bytes and no broker address | L1–L4 | **4** (property) + **3** (model, later) | the guest runtime's binary contains no broker client; a test dumps the guest's memory/environment/argv and greps for key material, secrets and the state-dir path; a TLA+ extension of `Custody.tla` where the guest is a process with no node |
| T2 | Every effect the guest performs is a channel request the host authorizes with today's checks | L1–L4 | **4** + **6** | the differential fuzzer (`delulu-fuzz`) run in guest mode asserts trace ⊆ row *and* that every trace record has a matching audited host request; a program cannot observe an effect the host did not perform |
| T3 | The sandbox policy is a pure function of (authority, grant, profile) | all | **4** | byte-identical policy JSON for identical inputs; a snapshot like core-invariance for the guide corpus |
| T4 | The host performs no effect outside the grant on the guest's behalf | all | **4** (existing containment/host tests re-run through the channel) | the C84/SYMLINK-DANGLE/hardlink/TOCTOU suites executed against the proxy |
| T5 | Under L1 on Linux the guest cannot open any host path or any socket | L1 | **4** + **7** for kernel bugs | escape tests attempt `open`, `openat2`, `connect`, `socket`, `mount`, `ptrace`, `/proc/self/root`, `/dev/kvm` from inside; each refused; a **mutant** launcher without Landlock/seccomp must fail the tests |
| T6 | Under L1 on Windows the guest cannot open host files outside its job and cannot create child processes | L1 | **4** + **7** | same shape: restricted-token child attempts `CreateFile` on user files, `CreateProcess`, named-pipe enumeration; mutant without the token fails |
| T7 | Under L1 on macOS the profile denies fs/net except the pipe | L1 | **4** + **7** (Seatbelt is deprecated: a platform assumption) | same shape via `sandbox-exec` |
| T8 | Resource limits terminate the guest, the host survives, and the diagnosis never recommends widening | L1–L2 | **4** | fork bomb / memory bomb / spin loop / disk fill inside the guest; the plugin `limits.rs` attribution rule re-used |
| T9 | Under L2 the guest has no network and no filesystem device | L2 | **4** + **7** (KVM/VMM bugs) | criterion 8 re-stated: from the guest, `connect` fails at socket creation (no NIC), name resolution is impossible, `169.254.169.254` unreachable, no block/fs devices in `/sys` |
| T10 | A killed guest is dead before the CLI reports it | L1–L2 | **4** | kill then probe pid/VMM; a mutant that reports before waiting fails |
| T11 | Two concurrent guests cannot observe each other | L1–L2 | **4** | two guests, distinct channels, shared nothing; a guest probing for the other's pipe/socket is refused; cross-check the audit log attributes each effect to the right guest |
| T12 | A malformed or oversized frame from the guest cannot crash or hang the host | L1–L4 | **6** + **4** | the channel fuzzer; a hang watchdog test (IPC-1's lesson: bound every read) |
| T13 | The guest image launched is the pinned one | L2 | **4** | hash mismatch refused; a flipped byte in the initramfs refused before launch |
| T14 | Identity separation: a guest launched as a different principal cannot read `broker.key` or the state dir | L1 where supported | **4** on POSIX (the P21 vectors re-run from inside a guest), **7** where the OS gives an unprivileged launcher no second identity | P21's five vectors from inside the guest |
| T15 | Levels are honest: a run reports the level it actually got, and a profile needing more refuses | all | **4** | `run --json` under each profile on each OS in CI; refusal codes witnessed |

**Category 7, named up front:** kernel and hypervisor exploits; hardware side channels; a host
whose kernel lacks Landlock/user namespaces (then L1 is *best-effort* and says so in
`host_guarantees`); the operator running the guest as themselves where the OS offers no
unprivileged identity separation; the operator's environment under L3; domain fronting or covert
channels through the *content* of legitimately granted effects (the language bounds reachability,
not behaviour — the same sentence as for foreign code); the audit anchor's own limit (rewriting
log and anchor together is still undetectable without an external witness).

## 4. Assumptions

1. The host `delulu` process is not compromised before launch (it is the broker's peer).
2. The kernel's namespaces, Landlock, seccomp, job objects, restricted tokens and Seatbelt do what
   their documentation says; probes verify presence, not correctness.
3. KVM and the VMM enforce the hardware boundary; the jailer is used as its authors prescribe
   (unique uid per VM, most restrictive seccomp, no serial console in production).
4. The channel transport is private by construction (owner-only pipe, per-VM vsock path in the
   jail, or an authenticated session) — the same assumption the broker transport already makes.
5. Determinism inputs (`--seed`, `--clock fixed`) are supplied by the host to the guest, so a
   sandboxed run is as replayable as an in-process one.

## 5. Known limitations and failure modes (designed to fail closed)

| Failure | Behaviour | Audit |
|---|---|---|
| launcher cannot apply a required control | refuse before launch with the missing control named; never launch weaker | `sandbox-refused` |
| channel does not connect within the deadline | kill the guest; report launch failure | `sandbox-launch-failed` |
| frame over bound / unknown request / unknown handle | kill the guest; `channel-violation` DL | `channel-violation` with the offending kind |
| limit exceeded | kill; DL with evidence-based attribution; no widening repair | `sandbox-limit` |
| guest exits unexpectedly | `guest_death` with status; exit 1 | `sandbox-death` |
| host revokes the guest's node | next request refused; kill-on-revoke | as today + `sandbox-kill` |
| operator `sandbox kill` | verified dead before the command returns | `sandbox-kill` |
| image hash mismatch | refuse | `sandbox-refused` |
| host lacks a probe-able control at run time (e.g. cgroup not writable) | run only if the profile permits *best-effort* for that control, and say so in `host_guarantees`; `hostile-agent` never permits best-effort | `sandbox-launch` carries the guarantees list |

## 6. Threat-specific notes

- **Traversal, symlinks, hardlinks, path confusion:** the guest never names a host path that the
  host does not resolve through `contains_on_disk`; the existing findings' witnesses become the
  proxy's tests. The TOCTOU residual (`CONTAIN-TOCTOU-1`) stays, and the deployment rule stays.
  **Two verified additions to the class (2026-09-17):** Windows reserved device names inside a
  grant are not refused (`NUL` reports success and writes nowhere; `CON` creates a real file through
  the verbatim path), and trailing dots and spaces are stripped by the OS after the containment
  decision was made on the unstripped spelling (NE-19, NE-20). Both are runtime-layer refusals
  (PS-0-06), not sandbox work — a jail below them would not have seen the difference either, because
  the *host* performs the write on the guest's behalf. The decision and the audit record must be
  made on the resolved name.
- **Device access, GPU, actuators:** devices are host-side capabilities; the guest gets handles;
  no `/dev` passthrough at any level. GPU isolation for `Cap[Compute]` remains the adapter's
  problem, outside the guest.
- **Process and namespace escape:** L1's seccomp allowlist excludes `unshare`, `setns`, `mount`,
  `ptrace`, `bpf`, `keyctl`, `io_uring`; Landlock scopes signals and abstract sockets (ABI 6);
  L2 has no such surface.
- **Network escape, DNS abuse, localhost, metadata:** the guest has no network at any level ≥ 1;
  the host performs `http.get` under the allowlist and can itself refuse literal IPs, link-local
  and loopback unless granted (a small host-side hardening worth doing in the same phase).
- **Credential, environment and secret leakage:** the guest's environment is empty but for the
  channel handle; secrets are host-only; `Secret.map` is the one exception, ruled separately.
- **Sandbox-to-sandbox:** distinct channels, distinct jails/jobs, distinct uids where possible.
- **Exhaustion:** limits per §5; the interpreter's depth bound remains inside the guest.
- **Timeout bypass, zombies, background persistence:** the host's watchdog kills the whole job /
  VM; PDEATHSIG and kill-on-close already cover host death.
- **IPC and sockets:** none reachable from the guest under L1 (seccomp + no netns) and L2.
- **Malformed images, malicious plugins and dependencies:** image hashes; the plugin load sequence
  host-side; dependency authority pins as today.
- **VM lifecycle and cleanup races, snapshot and restore contamination:** no snapshots in v1;
  orphan sweep; per-VM jail directories; concurrency tests in the test plan.
- **Realistic kernel/VMM surfaces:** the vsock device and the VMM API socket are the L2 surfaces;
  the API socket lives in the jail and is used only by the host launcher.

## 7. What stronger claims would require

- Saying "L1 contains hostile code": every T5–T8 witness green on all three OSes in CI, the mutant
  launchers red, and a SandboxEscapeBench-style scenario set (test plan §4) run against it with
  results published, including the failures.
- Saying "L2 contains hostile code": the above plus criterion 8 on a KVM runner, the image build
  reproducible, and the jailer configuration reviewed against Firecracker's production guide.
- Saying "the guest holds nothing": T1's model-checked extension, not only the tests.
- Saying anything about L3: nothing, until L4 exists — L3 reports `guarantees: unknown`.
- Saying "multi-tenant": never on one OS user; only with per-guest identities and L2.

Anything not listed here is not claimed.
